Wątki

Klasa Thread reprezentuje działanie uruchamiane w osobnym wątku. Kod wątku podajemy na dwa sposoby: przekazując funkcję do konstruktora (argument target) lub nadpisując metodę run() w podklasie.

Pierwszy sposób poznaliśmy na pierwszych zajęciach. Przypomnienie - funkcja jako target:

import threading
import time


def pracuj(nr, opoznienie):
    time.sleep(opoznienie)
    print(f"wątek {nr} skończył po {opoznienie} s")


t1 = threading.Thread(target=pracuj, args=(1, 0.2))
t2 = threading.Thread(target=pracuj, args=(2, 0.1))
t1.start()
t2.start()
print("main: wątki uruchomione")
t1.join()
t2.join()
print("main: koniec")
main: wątki uruchomione
wątek 2 skończył po 0.1 s
wątek 1 skończył po 0.2 s
main: koniec

W przypadku podklasy nadpisujemy tylko metody __init__() i run(). W konstruktorze koniecznie wywołujemy konstruktor klasy bazowej (super().__init__(...)), a pozostałych metod (start(), join(), …) nie ruszamy:

import threading
import time


class Pobieracz(threading.Thread):
    def __init__(self, url, opoznienie):
        super().__init__(name=f"pobieracz-{url}")
        self.url = url
        self.opoznienie = opoznienie
        self.rozmiar = None              # tu wątek zapisze wynik

    def run(self):                       # kod wykonywany w nowym wątku
        time.sleep(self.opoznienie)
        self.rozmiar = len(self.url) * 1000
        print(f"{self.name}: pobrano {self.url}")


watki = [Pobieracz("a.pl", 0.3), Pobieracz("bb.pl", 0.1), Pobieracz("ccc.pl", 0.2)]
for w in watki:
    w.start()
print("czy pierwszy żyje?", watki[0].is_alive())
for w in watki:
    w.join()
print("czy pierwszy żyje?", watki[0].is_alive())
print({w.url: w.rozmiar for w in watki})
czy pierwszy żyje? True
pobieracz-bb.pl: pobrano bb.pl
pobieracz-ccc.pl: pobrano ccc.pl
pobieracz-a.pl: pobrano a.pl
czy pierwszy żyje? False
{'a.pl': 4000, 'bb.pl': 5000, 'ccc.pl': 6000}

Konstruktor klasy Thread wygląda następująco:

class threading.Thread(group=None, target=None, name=None, args=(), kwargs={}, *, daemon=None)

Ten konstruktor powinien być zawsze wywoływany z argumentami nazwanymi. Argumenty:

  • target - funkcja (obiekt wywoływalny), którą wywoła metoda run(). Domyślnie None, czyli wątek nic nie robi (chyba że nadpiszemy run()).

  • args - krotka (lub lista) argumentów pozycyjnych dla target. Domyślnie ().

  • kwargs - słownik argumentów nazwanych dla target. Domyślnie {}.

  • name - nazwa wątku, przydatna w logach i w debuggerze. Domyślnie "Thread-N (funkcja)".

  • daemon - czy wątek jest demonem (poznaliśmy je na pierwszych zajęciach).

  • group - zarezerwowany na przyszłość, zawsze None.

start() a run()

Metoda start() tworzy nowy wątek systemowy i w nim wywołuje run(). Wolno ją wywołać tylko raz. Metoda run() to zwykła metoda - wywołana bezpośrednio wykona się w bieżącym wątku, bez żadnej współbieżności.

join() z limitem czasu

t.join() blokuje wątek wywołujący, aż wątek t się zakończy. Z argumentem timeout czekamy najwyżej podaną liczbę sekund. Uwaga: join() zawsze zwraca ``None`` - to, czy wątek naprawdę się zakończył, sprawdzamy metodą is_alive().

import threading
import time


def praca():
    time.sleep(0.5)
    print("praca: gotowe")


t = threading.Thread(target=praca)
t.start()
print("alive:", t.is_alive())
print("join(0.1) zwrócił:", t.join(timeout=0.1))

Wynik i wyjątek z wątku

Wartość zwrócona przez funkcję target przepada, a wyjątek zgłoszony w wątku nie trafia do wątku głównego - kończy tylko ten wątek. Wynik możemy zapisać we wspólnej strukturze (każdy wątek pisze w swoje miejsce) lub w atrybucie podklasy, jak w klasie Pobieracz.

import threading


def kwadrat(x, wyniki, i):
    wyniki[i] = x * x          # każdy wątek pisze w SWOJE miejsce listy


dane = [3, 1, 4, 1, 5]
wyniki = [None] * len(dane)
watki = [threading.Thread(target=kwadrat, args=(x, wyniki, i)) for i, x in enumerate(dane)]
for w in watki:
    w.start()
for w in watki:
    w.join()
print(wyniki)
[9, 1, 16, 1, 25]

Wyjątki z wątków obsługuje funkcja threading.excepthook - domyślnie wypisuje traceback. Możemy ją podmienić, np. by zbierać błędy w liście i obsłużyć je w wątku głównym:

import threading

bledy = []


def zbieraj(args):
    bledy.append((args.thread.name, args.exc_type.__name__, str(args.exc_value)))


def dziel(a, b):
    print(f"{a} / {b} = {a / b}")


threading.excepthook = zbieraj
watki = [threading.Thread(target=dziel, args=(10, b), name=f"dziel-przez-{b}") for b in (2, 0, 5)]
for w in watki:
    w.start()
for w in watki:
    w.join()
threading.excepthook = threading.__excepthook__     # przywróć domyślną obsługę

print("main działa dalej, błędy w wątkach:", bledy)

Dane lokalne wątku

Podczas gdy niektóre zasoby muszą być współdzielone i chronione zamkiem, inne powinny być prywatne dla wątku. Obiekt threading.local() wygląda jak jedna zmienna, ale każdy wątek widzi w nim własne atrybuty (np. własne połączenie z bazą danych).

Najpierw zwykła zmienna globalna - wszystkie wątki korzystają z tej samej zmiennej i sobie przeszkadzają:

import threading
import time

licznik = 0                      # jedna zmienna dla wszystkich wątków


def zadanie(nazwa):
    global licznik
    licznik = 0
    for _ in range(5):
        time.sleep(0.01)
        licznik += 1
    print(nazwa, licznik)


watki = [threading.Thread(target=zadanie, args=(f"W{i}",)) for i in range(3)]
for w in watki:
    w.start()
for w in watki:
    w.join()
W0 13
W2 14
W1 15

Ten sam kod z threading.local() - każdy wątek ma swoją kopię atrybutu licznik:

import threading
import time

dane = threading.local()         # atrybuty osobne dla każdego wątku


def zadanie(nazwa):
    dane.licznik = 0
    for _ in range(5):
        time.sleep(0.01)
        dane.licznik += 1
    print(nazwa, dane.licznik)


watki = [threading.Thread(target=zadanie, args=(f"W{i}",)) for i in range(3)]
for w in watki:
    w.start()
for w in watki:
    w.join()
print("w wątku głównym:", getattr(dane, "licznik", "brak atrybutu"))

Kiedy wątki przyspieszają?

Na wykładzie mówiliśmy, że w standardowym CPythonie GIL pozwala wykonywać kod Pythona tylko jednemu wątkowi naraz. Wątki przyspieszają więc zadania, które głównie czekają (sieć, dysk, czujniki - podczas czekania GIL jest zwalniany), ale nie przyspieszają obliczeń:

import threading
import time


def pobierz(url):
    time.sleep(0.5)                       # udaje czekanie na odpowiedź serwera


def policz(n):
    return sum(i * i for i in range(n))   # czyste obliczenia


def zmierz(opis, funkcja, argumenty, w_watkach):
    start = time.perf_counter()
    if w_watkach:
        watki = [threading.Thread(target=funkcja, args=(a,)) for a in argumenty]
        for w in watki:
            w.start()
        for w in watki:
            w.join()
    else:
        for a in argumenty:
            funkcja(a)
    print(f"{opis:<26} {time.perf_counter() - start:5.2f} s")


zmierz("I/O, sekwencyjnie", pobierz, range(5), False)
zmierz("I/O, 5 wątków", pobierz, range(5), True)
zmierz("CPU, sekwencyjnie", policz, [2_000_000] * 4, False)
zmierz("CPU, 4 wątki", policz, [2_000_000] * 4, True)

I/O, 5 wątków               0.50 s
CPU, sekwencyjnie           0.72 s
CPU, 4 wątki                1.71 s

Synchronizacja

Synchronizacja to koordynacja pracy wątków. Ma dwa cele:

  • wzajemne wykluczanie - kontrola dostępu do współdzielonych danych. Sekcja krytyczna to fragment kodu korzystający ze wspólnych danych, który w danej chwili może wykonywać co najwyżej jeden wątek,

  • koordynacja kolejności - wątek czeka, aż inny osiągnie znany punkt (skończy pracę, przygotuje dane). Przykłady: join(), Condition, Event.

Wyścig (race condition)

Na wykładzie 1 obiecaliśmy sprawdzić na laboratoriach, czy licznik += 1 w czterech wątkach daje poprawny wynik. Sprawdźmy dwie wersje - z operacją += wpisaną bezpośrednio w pętlę oraz z tą samą operacją wykonaną przez wywołanie funkcji:

import threading

licznik = 0


def plus1(x):
    return x + 1


def dodawaj(n):
    global licznik
    for _ in range(n):
        licznik += 1


def dodawaj_przez_funkcje(n):
    global licznik
    for _ in range(n):
        licznik = plus1(licznik)          # odczyt ... wywołanie funkcji ... zapis


for funkcja in (dodawaj, dodawaj_przez_funkcje):
    wyniki = []
    for proba in range(3):
        licznik = 0
        watki = [threading.Thread(target=funkcja, args=(1_000_000,)) for _ in range(4)]
        for w in watki:
            w.start()
        for w in watki:
            w.join()
        wyniki.append(licznik)
    print(f"{funkcja.__name__:<22} {wyniki}   (oczekujemy 4000000)")
dodawaj                [4000000, 4000000, 4000000]   (oczekujemy 4000000)
dodawaj_przez_funkcje  [2061123, 2232121, 2182667]   (oczekujemy 4000000)

W CPythonie 3.13 (z GIL) pierwsza wersja zwykle daje poprawny wynik: interpreter przełącza wątki tylko w wybranych miejscach kodu bajtowego, a samo licznik += 1 w pętli rzadko trafia pomiędzy odczyt i zapis. To nie jest gwarancja - wystarczy wywołanie funkcji między odczytem a zapisem (wersja druga), by zgubić nawet połowę zwiększeń. W innej wersji interpretera (np. bez GIL) błąd pojawia się także w pierwszej wersji.

Zamiast liczyć na szczęście, chronimy sekcję krytyczną zamkiem.

Zamek (Lock)

Lock (mutex) jest w jednym z dwóch stanów: odblokowany lub zablokowany. Nowy zamek jest odblokowany. Gdy jeden wątek uzyska blokadę, kolejne próby jej uzyskania czekają, aż zostanie zwolniona. Metody:

  • acquire(blocking=True, timeout=-1) - zajmuje zamek. Jeżeli zamek jest zajęty, czeka na jego zwolnienie. Z blocking=False nie czeka wcale, a z timeout=t czeka najwyżej t sekund. Zwraca True, jeśli udało się zająć zamek, False w przeciwnym razie.

  • release() - zwalnia zamek. Jeśli czeka kilka wątków, zamek dostaje dokładnie jeden z nich (bez gwarancji kolejności). Zwykły Lock nie ma właściciela: zwolnić go może dowolny wątek. Wywołanie na odblokowanym zamku zgłasza RuntimeError.

  • locked() - zwraca True, jeśli zamek jest zajęty.

import threading

lock = threading.Lock()
print(lock.acquire())                  # zamek wolny: zajmujemy go
print(lock.locked())
print(lock.acquire(blocking=False))    # zajęty: nie czekamy
print(lock.acquire(timeout=0.5))       # zajęty: czekamy najwyżej 0.5 s
lock.release()
print(lock.locked())
lock.release()                         # zwolnienie wolnego zamka

Poniżej przykład symulujący błąd synchronizacji. Funkcja odczytuje licznik, „liczy” przez 0.1 s i zapisuje wynik - drugi wątek zdąży w tym czasie odczytać starą wartość:

import threading
import time

counter = 0


def increase(by):
    global counter
    local_counter = counter
    local_counter += by
    time.sleep(0.1)
    counter = local_counter
    print(f"counter = {counter}")


t1 = threading.Thread(target=increase, args=(1,))
t2 = threading.Thread(target=increase, args=(2,))
t1.start()
t2.start()
t1.join()
t2.join()
print(f"The final counter is {counter}")
counter = 1counter = 2

The final counter is 2

Jeżeli dwa komunikaty skleiły się w jednej linii (np. counter = 1counter = 2), to również jest wyścig: print zapisuje tekst i znak końca linii w dwóch osobnych operacjach, a drugi wątek może wpisać swój tekst pomiędzy nimi. Takie sklejenia mogą pojawić się w wynikach wielu programów w tym notatniku.

Ten sam kod z zabezpieczeniem dostępu za pomocą zamka. Teraz tylko jeden wątek może wykonywać sekcję krytyczną. Zamiast pary acquire() / release() używamy instrukcji with - zamek zostanie zwolniony nawet wtedy, gdy w sekcji krytycznej poleci wyjątek:

import threading
import time

counter = 0
lock = threading.Lock()


def increase(by):
    global counter
    with lock:                       # lock.acquire() ... lock.release()
        local_counter = counter
        local_counter += by
        time.sleep(0.1)
        counter = local_counter
        print(f"counter = {counter}")


t1 = threading.Thread(target=increase, args=(1,))
t2 = threading.Thread(target=increase, args=(2,))
t1.start()
t2.start()
t1.join()
t2.join()
print(f"The final counter is {counter}")
counter = 1
counter = 3
The final counter is 3

Uwaga! Samo lock.acquire() … lock.release() bez try / finally jest niebezpieczne: wyjątek w sekcji krytycznej zostawi zamek zablokowany na zawsze, a pozostałe wątki zawisną. Instrukcja with lock: robi try / finally za nas.

Typowy wyścig typu „sprawdź, potem działaj”: dwa wątki jednocześnie wypłacają 80 zł z konta, na którym jest 100 zł. Sprawdzenie salda i wypłata to dwa kroki, a wątek może zostać przełączony pomiędzy nimi:

import threading
import time

saldo = 100


def wyplac(kwota):
    global saldo
    if saldo >= kwota:          # sprawdź...
        time.sleep(0.01)        # tu wątek zostaje przełączony
        saldo -= kwota          # ...i działaj
        print(f"{threading.current_thread().name}: wypłacono {kwota} zł")


watki = [threading.Thread(target=wyplac, args=(80,)) for _ in range(2)]
for w in watki:
    w.start()
for w in watki:
    w.join()
print("saldo:", saldo)
Thread-59 (wyplac): wypłacono 80 zł
Thread-60 (wyplac): wypłacono 80 zł
saldo: -60

Zrób to sam!

  1. Popraw funkcję wyplac za pomocą zamka tak, by saldo nigdy nie spadło poniżej zera. Czy wystarczy objąć zamkiem samą linię saldo -= kwota? Sprawdź.

  2. Usuń time.sleep(0.01) z wersji bez zamka i uruchom program 1000 razy w pętli (pamiętaj o przywróceniu salda). Ile razy saldo spadło poniżej zera? Dlaczego brak błędu w testach nie dowodzi poprawności programu?

Zamek RLock

Zwykły Lock nie pamięta, który wątek go zajął. Jeśli wątek, który już trzyma zamek, spróbuje zająć go ponownie, będzie czekał w nieskończoność - na samego siebie (zakleszczenie, ang. deadlock). W Jupyterze takie zawieszenie wymaga restartu kernela, dlatego drugie acquire() wywołujemy z limitem czasu:

import threading

lock = threading.Lock()

lock.acquire()
print("pierwsze acquire: zamek zajęty")
udalo_sie = lock.acquire(timeout=1)      # bez timeout program zawiesiłby się tutaj na zawsze
print("drugie acquire w tym samym wątku:", udalo_sie)
lock.release()
pierwsze acquire: zamek zajęty
drugie acquire w tym samym wątku: False

Zamek wielokrotnego wejścia (RLock, reentrant lock) pamięta właściciela i licznik wejść. Ten sam wątek może go zająć wiele razy, ale musi wywołać release() tyle razy, ile acquire(). RLock przydaje się, gdy metody chronione tym samym zamkiem wywołują się nawzajem:

import threading


class Konto:
    def __init__(self, nazwa, saldo):
        self.nazwa = nazwa
        self.saldo = saldo
        self.lock = threading.RLock()     # z Lock() metoda przelej() zawiesi program

    def wplac(self, kwota):
        with self.lock:
            self.saldo += kwota

    def wyplac(self, kwota):
        with self.lock:
            if self.saldo < kwota:
                raise ValueError(f"{self.nazwa}: brak środków")
            self.saldo -= kwota

    def przelej(self, cel, kwota):
        with self.lock:                   # 1. wejście
            self.wyplac(kwota)            # 2. wejście tego samego wątku
            cel.wplac(kwota)


a, b = Konto("A", 100), Konto("B", 0)
watki = [threading.Thread(target=a.przelej, args=(b, 30)) for _ in range(3)]
for w in watki:
    w.start()
for w in watki:
    w.join()
print(a.saldo, b.saldo)
10 90

Wait / notify

Producent-konsument

Producenci wytwarzają dane i wkładają je do wspólnego bufora, a konsumenci wyjmują je i przetwarzają. Obie strony pracują we własnym tempie, a bufor wyrównuje chwilowe różnice prędkości. Gdy bufor jest pusty, konsument powinien czekać - ale jak?

Z samym zamkiem zostaje tylko aktywne czekanie (busy waiting): konsument w pętli sprawdza, czy coś się pojawiło. Policzmy, ile razy sprawdzi bufor, zanim producent (po 0.5 s) włoży do niego jeden element:

import threading
import time

bufor = []
lock = threading.Lock()


def producent():
    time.sleep(0.5)
    with lock:
        bufor.append("dane")


def konsument():
    sprawdzen = 0
    while True:                     # aktywne czekanie
        with lock:
            sprawdzen += 1
            if bufor:
                x = bufor.pop(0)
                break
    print(f"konsument: mam {x!r}, sprawdzałem bufor {sprawdzen:,} razy")


watki = [threading.Thread(target=konsument), threading.Thread(target=producent)]
for w in watki:
    w.start()
for w in watki:
    w.join()
konsument: mam 'dane', sprawdzałem bufor 1,371,763 razy

Przez pół sekundy konsument zużywał cały rdzeń procesora (i walczył o GIL z producentem). Dodanie time.sleep(0.01) w pętli zmniejsza zużycie, ale wprowadza opóźnienie reakcji. Zamek chroni sekcję krytyczną, ale nie potrafi powiadomić innych wątków, że stan się zmienił. Potrzebujemy operacji „uśpij mnie, aż ktoś zmieni stan” (wait) oraz „obudź czekających” (notify).

Bufor ograniczony na zmiennej warunkowej

Producent czeka, gdy bufor jest pełny, a konsument - gdy jest pusty. Warunek zawsze sprawdzamy w pętli ``while``, a nie if: po obudzeniu warunek mógł już przestać być prawdziwy, bo między notify() a odzyskaniem zamka działał inny wątek (zdarzają się też tzw. fałszywe wybudzenia). Na tej samej zmiennej warunkowej czekają producenci i konsumenci, dlatego używamy notify_all():

import threading
import time
from collections import deque


class Bufor:
    def __init__(self, pojemnosc):
        self.dane = deque()
        self.pojemnosc = pojemnosc
        self.cond = threading.Condition()

    def put(self, x):
        with self.cond:
            while len(self.dane) == self.pojemnosc:
                self.cond.wait()              # pełny: czekaj
            self.dane.append(x)
            self.cond.notify_all()            # obudź czekających

    def get(self):
        with self.cond:
            while not self.dane:
                self.cond.wait()              # pusty: czekaj
            x = self.dane.popleft()
            self.cond.notify_all()
            return x


def producent(b):
    for i in range(5):
        b.put(i)
        print(f"P: włożyłem {i}")
    b.put(None)                               # wartownik: koniec danych


def konsument(b):
    while (x := b.get()) is not None:
        time.sleep(0.1)                       # wolny konsument
        print(f"    K: przetworzyłem {x}")


b = Bufor(pojemnosc=2)
watki = [threading.Thread(target=producent, args=(b,)),
         threading.Thread(target=konsument, args=(b,))]
for w in watki:
    w.start()
for w in watki:
    w.join()

import threading
import queue
import time

q = queue.Queue(maxsize=3)        # bufor ograniczony


def producent():

            break
        time.sleep(0.1)
        print(nazwa, "przetworzył", x)


watki = [threading.Thread(target=producent)]

Zdarzenie (Event)

Event to flaga logiczna z możliwością czekania: set() ustawia ją na True i budzi wszystkich czekających, clear() ustawia na False, wait(timeout) czeka, aż flaga będzie prawdziwa, a is_set() zwraca jej stan. W odróżnieniu od notify() zdarzenie pamięta stan: wait() po set() wraca od razu. Event nie chroni danych - to sygnał, a nie zamek.

Typowe użycie 1: wspólny start wielu wątków.

import threading
import time

watki = [threading.Thread(target=biegacz, args=(i,)) for i in range(3)]

    w.start()

Semafory

Jest to jedna z najstarszych metod synchronizacji w historii informatyki, wymyślona przez Edsgera W. Dijkstrę w 1965 roku (używał nazw P() i V() zamiast acquire() i release()). Najprościej mówiąc semafor to zamek, który wpuszcza do sekcji krytycznej n wątków jednocześnie.

Semafor zarządza wewnętrznym licznikiem, który jest zmniejszany przez każde wywołanie funkcji acquire() i zwiększany przez każde wywołanie funkcji release(). Licznik nigdy nie spada poniżej zera; kiedy acquire() stwierdzi, że wartość licznika wynosi zero, blokuje się, czekając, aż jakiś inny wątek wywoła release().

Przykład: 8 użytkowników korzysta z bazy danych, która pozwala na tylko 3 jednoczesne sesje. Każdy wątek wypisuje czas względem startu programu, więc widać, kto czeka:

import threading
import time
import random

random.seed(3)
polaczenia = threading.BoundedSemaphore(3)    # 3 sesje bazy danych
licznik_lock = threading.Lock()
aktywne = maks = 0
T0 = time.perf_counter()


def log(msg):
    print(f"{time.perf_counter() - T0:4.1f} s  {msg}")


def uzytkownik(nr, czas_zapytania):
    global aktywne, maks
    with polaczenia:                          # acquire() ... release()
        with licznik_lock:                    # aktywne to wspólne dane: osobny zamek
            aktywne += 1
            maks = max(maks, aktywne)
            log(f"U{nr} wchodzi   (aktywnych: {aktywne})")
        time.sleep(czas_zapytania)            # zapytanie do bazy
        with licznik_lock:
            aktywne -= 1
            log(f"U{nr} wychodzi  (aktywnych: {aktywne})")


watki = [threading.Thread(target=uzytkownik, args=(i, round(random.uniform(0.2, 0.6), 1))) for i in range(8)]
for w in watki:
    w.start()
for w in watki:
    w.join()
print("maks. jednocześnie:", maks)

Bariera (Barrier)

Barrier(n) to punkt spotkania: każdy wątek wywołuje wait() i czeka, aż zrobi to n wątków - wtedy ruszają wszystkie naraz. Opcjonalna funkcja action wykonuje się raz, gdy wszyscy dotrą do bariery. Bariera jest wielokrotnego użytku, więc nadaje się do algorytmów etapowych, w których etap k+1 potrzebuje wyników wszystkich wątków z etapu k.

Przykład: trzy wątki w każdej rundzie liczą sumę swojego fragmentu danych, a po każdej rundzie (gdy wszystkie skończą) funkcja action łączy wyniki:

import threading
import random
import time

N = 3
czesciowe = [0] * N
runda = 0


def podsumuj():                       # wykonuje się raz na rundę, w jednym z wątków
    global runda
    runda += 1
    print(f"--- runda {runda}: suma = {sum(czesciowe)}")


bariera = threading.Barrier(N, action=podsumuj)


def licz(nr):
    for r in range(3):
        time.sleep(random.uniform(0.05, 0.2))
        czesciowe[nr] = sum(range(nr * 100, (nr + 1) * 100)) * (r + 1)
        print(f"W{nr}: runda {r + 1} gotowa")
        bariera.wait()                # dalej dopiero, gdy dojdą wszyscy


watki = [threading.Thread(target=licz, args=(i,)) for i in range(N)]
for w in watki:
    w.start()
for w in watki:
    w.join()

Połączmy poznane mechanizmy w jeden program, który przypomina system przetwarzania strumieniowego z wykładu 1:

  • trzy wątki czujników (producenci) co 0.1 s mierzą temperaturę i wkładają pomiary do kolejki queue.Queue(maxsize=5),

  • wątek agregatora (konsument) wyjmuje pomiary i liczy średnią dla każdego czujnika,

  • wątek główny po 1.5 s ustawia zdarzenie stop; czujniki kończą pracę, a gdy wszystkie się zatrzymają, kolejka zostaje zamknięta (shutdown()), co kończy pracę agregatora.

import threading
import queue
import random
import time
from collections import defaultdict

random.seed(1)
pomiary = queue.Queue(maxsize=5)
stop = threading.Event()


def czujnik(nazwa, srednia):
    while not stop.is_set():
        pomiary.put((nazwa, round(random.gauss(srednia, 1.5), 1)))
        stop.wait(0.1)


def agregator(wyniki):
    sumy = defaultdict(float)
    liczniki = defaultdict(int)
    while True:
        try:
            nazwa, temp = pomiary.get()
        except queue.ShutDown:
            break
