multiprocessing

multiprocessing to pakiet obsługujący tworzenie procesów przy użyciu interfejsu API podobnie do modułu thread.

Pakiet multiprocessing oferuje zarówno lokalną, jak i zdalną współbieżność, skutecznie omijając globalną blokadę interpretera, używając podprocesów zamiast wątków. Dzięki temu moduł wieloprocesorowy pozwala programiście na pełne wykorzystanie wielu procesorów na danej maszynie. Działa zarówno na systemie Unix, jak i Windows.

W przetwarzaniu multiprocessing procesy są tworzone przez utworzenie obiektu Process, a następnie wywołanie jego metody start().

from time import sleep
from multiprocessing import Process

def task():
    sleep(1)
    print('This is from another process')

if __name__ == '__main__':
    process = Process(target=task)
    process.start()
    print('Waiting for the process...')
    process.join()

Podobnie możemy tworzyć proces jako podklase klasy Process:

from time import sleep
from multiprocessing import Process

class CustomProcess(Process):
    def run(self):
        sleep(1)
        print('This is coming from another process')

if __name__ == '__main__':
    process = CustomProcess()
    process.start()
    print('Waiting for the process to finish')
    process.join()

Dane między procesami być przechowywane na mapie pamięci współdzielone przy użyciu Value lub Array.

Zmienne współdzielone oznaczają, że zmiany dokonane w jednym procesie są zawsze propagowane i udostępniane innym procesom. Wystąpienie multiprocessing.Value można zdefiniować w konstruktorze klasy jako zmienną. Konstruktor klasy multiprocessing.Value wymaga od nas określenia typu danych oraz wartości początkowej. Definicje konstruktorów obiektów:

multiprocessing.Array(typecode_or_type, size_or_initializer, *, lock=True)

multiprocessing.Value(typecode_or_type, *args, lock=True)

Typy z moduly ctypes: ‘i’ - int, ‘d’ - double, c_char - char, c_bool - bool, c_wchar_p - String.

Jeśli blokada ma wartość True (wartość domyślna), tworzony jest nowy obiekt blokady w celu synchronizacji dostępu do wartości. Jeśli lock jest obiektem Lock lub RLock, zostanie użyty do synchronizacji dostępu do wartości. Jeśli blokada ma wartość False, dostęp do zwróconego obiektu nie będzie automatycznie chroniony blokadą, więc niekoniecznie będzie „bezpieczny dla procesu”.

Na przykład:

from multiprocessing import Process, Value, Array
from ctypes import Structure, c_bool

def f(n, a, m):
    n.value = 3.1415927
    m.value = True
    for i in range(len(a)):
        a[i] = -a[i]

if __name__ == '__main__':
    num = Value('d', 0.0)
    bools = Value(c_bool, False)
    arr = Array('i', range(10))

    p = Process(target=f, args=(num, arr, bools))
    p.start()
    p.join()

    print(num.value)
    print(bools.value)
    print(arr[:])

Jak tworzone są nowe procesy? Python udostępnia trzy metody: fork (kopia bieżącego procesu, tylko Unix), spawn (nowy interpreter uruchamiany od zera, domyślna na Windows i macOS) oraz forkserver. Jupyter działa tu na Linuxie, więc w Pythonie 3.13 domyślną metodą jest fork (od Pythona 3.14 domyślnym na Linuxie będzie forkserver). Uruchom program u siebie na systemie Windows i porównaj wynik.

Race condition

Przykład: jeden wątek dodaje, drugi odejmuje tę samą wartość tyle samo razy, więc wynik powinien wynosić 0. Sprawdzamy dwie wersje - z operacją += wpisaną bezpośrednio w pętlę oraz z tą samą operacją wykonaną przez wywołanie funkcji:

from threading import Thread

def zmien(x, delta):
    return x + delta

def adder(amount, repeats):
    global value
    for _ in range(repeats):
        value += amount*2

def subtractor(amount, repeats):
    global value
    for _ in range(repeats):
        value -= amount*2

def adder_przez_funkcje(amount, repeats):
    global value
    for _ in range(repeats):
        value = zmien(value, amount*2)      # odczyt ... wywołanie funkcji ... zapis

def subtractor_przez_funkcje(amount, repeats):
    global value
    for _ in range(repeats):
        value = zmien(value, -amount*2)

for dodaj, odejmij in ((adder, subtractor), (adder_przez_funkcje, subtractor_przez_funkcje)):
    value = 0
    adder_thread = Thread(target=dodaj, args=(10, 500000))
    adder_thread.start()
    subtractor_thread = Thread(target=odejmij, args=(10, 500000))
    subtractor_thread.start()
    adder_thread.join()
    subtractor_thread.join()
    print(f'{dodaj.__name__:<22} Value: {value}')
adder                  Value: 0
adder_przez_funkcje    Value: -112920

W CPythonie 3.13 (z GIL) pierwsza wersja zwykle daje poprawny wynik 0: interpreter przełącza wątki tylko w wybranych miejscach kodu bajtowego, a samo value += ... w pętli rzadko trafia pomiędzy odczyt i zapis. To nie jest gwarancja - wystarczy wywołanie funkcji między odczytem a zapisem (wersja druga), by wynik był zupełnie przypadkowy. W wersji interpretera bez GIL błąd pojawia się także w pierwszej wersji. Jedyną gwarancją poprawności jest zamek (Lock).

Zakleszczenie

Przykład: wątki czekają na siebie nawzajem (złe użycie join()). Wątek główny czeka na nowy wątek, a nowy wątek czeka na wątek główny. Bez limitu czasu program zawiesiłby się na zawsze (w Jupyterze trzeba by zrestartować kernel), dlatego używamy join(timeout=...) i sprawdzamy is_alive():

from threading import current_thread
from threading import Thread

def task(other, timeout):
    print(f'[{current_thread().name}] waiting on [{other.name}]...')
    other.join(timeout=timeout)      # bez timeout: czekanie w nieskończoność
    if other.is_alive():
        print(f'[{current_thread().name}] [{other.name}] nadal działa po {timeout} s - zakleszczenie!')
    else:
        print(f'[{current_thread().name}] [{other.name}] zakończył się')

main_thread = current_thread()
new_thread = Thread(target=task, args=(main_thread, 2))
new_thread.start()
task(new_thread, 3)

Przykład złe blokowanie locków: wątek 1 zajmuje zamki w kolejności lock1, lock2, a wątek 2 w kolejności odwrotnej. Każdy trzyma jeden zamek i czeka na drugi. Drugi zamek zajmujemy z limitem czasu, żeby wykryć zakleszczenie zamiast zawiesić program:

from time import sleep
from threading import Thread
from threading import Lock

def task(number, lock1, lock2):
    print(f'Thread {number} acquiring lock 1...')
    with lock1:
        sleep(1)
        print(f'Thread {number} acquiring lock 2...')
        if lock2.acquire(timeout=3):     # bez timeout: czekanie w nieskończoność
            lock2.release()
            print(f'Thread {number} done')
        else:
            print(f'Thread {number}: nie mogę zająć lock 2 przez 3 s - zakleszczenie!')

lock1 = Lock()
lock2 = Lock()
thread1 = Thread(target=task, args=(1, lock1, lock2))
thread2 = Thread(target=task, args=(2, lock2, lock1))
thread1.start()
thread2.start()

W Pythonie 3.13 wątki wykonują się tu na zmianę. W Pythonie 3.9, na którym powstał ten przykład, ten sam kod nadal głodził wątek 1: wątek 0 zwalniał zamek i od razu zajmował go ponownie, zanim czekający wątek zdążył się obudzić. Dokumentacja nie gwarantuje, że zamek jest sprawiedliwy - kolejność zależy od wersji interpretera i systemu operacyjnego.

Nie każdy mechanizm zachowuje się tak samo. Semaphore(1) działa jak zamek, ale jest zaimplementowany w Pythonie (na zmiennej warunkowej) i w tym przykładzie głodzi wątek 1 także w Pythonie 3.13:
